The Problem

White-label apps get hard when every customer becomes a fork

Brand variants multiply fast

Each customer wants its own logo, theme, feature set, content, and launch date. Separate forks turn those requests into maintenance you pay for on every release.

Store reviews slow tenant fixes

A menu typo or onboarding fix for one tenant should not wait for a new binary and store review, often 24–48 hours, sometimes much longer.

Global releases are too blunt

One global update can break every brand at once. One fork per brand slows the whole team down. You need a release lane per tenant.

Common setups

What white-label looks like in a Capgo app

Customer-branded SaaS app

Each business customer gets its own logo, theme, onboarding copy, and feature set, and receives updates on its own channel.

Franchise or location app

Mini-app marketplace

The Solution

One app shell, a release lane per tenant

The native shell stays shared. Each tenant's web layer moves through its own channel.

Channel per tenant

Each tenant, franchise, or workspace gets a channel. Ship to one tenant or to all of them, and roll back one channel without touching the others.

Self-assign at runtime

How it works

How white-label teams ship with Capgo

One Capacitor codebase, one channel per tenant. The commands and code are from the Capgo CLI and updater docs.

  1. 1

    Create a channel for each tenant

    Each tenant gets a channel with its own bundle and history. Allow self-assignment so the app can move a device onto it.

    npx @capgo/cli@latest channel add acme com.example.app --self-assign
npx @capgo/cli@latest channel add globex com.example.app --self-assign
    Channels docs
  2. 2

    Upload each tenant's bundle

    Build the web layer with the tenant's theme and config, then upload it to that tenant's channel only. Other tenants keep their current bundle.

    npx @capgo/cli@latest bundle upload --channel acme
npx @capgo/cli@latest bundle upload --channel globex
    Rollback docs
  3. 3

    Move the device to its tenant at sign-in

    After sign-in, call setChannel() with the tenant's channel. The choice is stored on the device and takes effect on the next update check.

    import { CapacitorUpdater } from '@capgo/capacitor-updater'

await CapacitorUpdater.setChannel({
  channel: tenant.channel,
  triggerAutoUpdate: true,
})
    setChannel() reference
  4. 4

    Build branded shells in the cloud

    When a tenant needs its own store listing, icon, or permissions, build that flavor or scheme with Capgo Build. No Mac of your own needed.

    npx @capgo/cli@latest build request com.acme.app --platform android --android-flavor acme
npx @capgo/cli@latest build request com.acme.app --platform ios --ios-scheme Acme

FAQ

White-label questions

What teams ask before running many brands on one Capgo setup.

Do we need a separate Capgo app for every brand?

Only when each brand has its own app ID in the stores. One store app that serves many tenants is one Capgo app with a channel per tenant. Separate branded store apps are separate Capgo apps, each with its own channels.

Channels docs

Can a user switch tenants inside the app?

Yes. If the tenant's channel allows self-assignment, call setChannel() from the app. On current plugin versions the choice is stored on the device and used on the next update check.

setChannel() reference

What if some tenants are on an older native version?

Use version targeting. Block major updates on a channel, or set a minimum native version on a bundle, so older shells keep a bundle they can run.

Version targeting docs

Can we roll back one tenant without affecting the others?

Yes. Each channel keeps its own bundle history. Roll the tenant's channel back to an earlier bundle, and the other channels keep what they have.

Rollback docs

What still needs a store release?

App names, icons, permissions, native plugins, and native code live in the binary. Capgo Build can build each flavor or scheme and upload it to App Store Connect and Google Play.
