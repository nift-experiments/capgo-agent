The Problem

A store release is a slow way to ship a small fix

The store-only fix path

1

Find the bug

Monitoring or support reports a broken screen. The fix is a few lines of JavaScript or CSS.

2

Build a new binary

You bump the version, build for iOS and Android, and prepare two store submissions.

3

Wait for review

Store review is often 24–48 hours, sometimes much longer. A rejection starts the wait again.

4

Wait for users to update

After approval, each user still has to install the new version. Until then, they run the old code.

Each step adds time between the fix being ready and the fix running on your users' devices.

Why store fixes reach users slowly

24–48h+

Typical store review time

Apple and Google review every new binary. Review is often 24–48 hours, sometimes much longer, and a rejection means resubmitting.

Per user

Store updates depend on each device

A store update reaches a device only when the user, or their auto-update setting, installs it. Some devices stay on old builds for a long time.

2 stores

Two submissions for every fix

The same web fix goes through the App Store and Google Play separately, each with its own review and release.

The Solution

How a live update reaches your users

This is Capgo's default update behavior. No update prompts, no forced restarts, and no store submission for web-layer changes.

Default update flow

  1. 1

    The app checks for updates

    When the app comes to the foreground, and every 10 minutes while it stays open, the updater asks Capgo for the channel's latest bundle.

    On foreground

  2. 2

    It downloads in the background

    The new bundle downloads while the user keeps using the current version. With delta updates, only changed files download.

    No interruption

  3. 3

    It switches on the next resume

    When the user leaves the app, the updater installs the bundle. The next time they open it, they run the new version.

    Next foreground

Need users to see the new version as soon as they open the app? Direct update modes apply it at launch while the splash screen is shown.

See direct updates

How it works

How production teams ship a fix with Capgo

A typical release for a Capacitor app that is already in the stores. Every command below is from the Capgo CLI docs.

  1. 1

    Set up the updater once

    Run the setup wizard, then make sure your app calls notifyAppReady() after it starts. A bundle that never makes that call rolls back by itself.

    npx @capgo/cli@latest init
# in your app start-up code
await CapacitorUpdater.notifyAppReady()
    notifyAppReady() docs
  2. 2

    Upload the fix to a slice of production

    Use --delta so devices fetch only changed files, and --rollout to start with a small share of devices. Everyone else stays on the stable bundle.

    npx @capgo/cli@latest bundle upload --channel production --delta --rollout 5
    Progressive rollouts docs
  3. 3

    Let Capgo stop a bad rollout

    Turn on auto-pause with a failure-rate threshold (500 basis points is 5%). If failures pass it, Capgo rolls the rollout back. Check the new version in Observe while it runs.

    npx @capgo/cli@latest channel set production \
  --auto-pause-enabled \
  --auto-pause-failure-rate-bps 500 \
  --auto-pause-action rollback
    Observe docs
  4. 4

    Promote to everyone

    When the numbers look right, promote the bundle to every device on the channel. If not, send the rollout cohort back to stable.

    npx @capgo/cli@latest channel set production --rollout-promote
# or, if something looks wrong
npx @capgo/cli@latest channel set production --rollout-rollback
    Rollbacks docs

Built for production releases

The controls production teams use to ship often without surprising users.

Delta updates

Upload with --delta and devices download only the files that changed since their current bundle. Large assets that rarely change are downloaded once.

  • Smaller downloads for users on slow or metered networks
  • In the default mode, updates apply between sessions, not in the middle of one
Delta updates docs

--delta

Only changed files are downloaded

Progressive rollout with auto-pause

Send a new bundle to a random, sticky share of a channel while everyone else stays on the stable bundle. Raise the percentage, promote it, or roll it back from the CLI or console.

  • Auto-pause can pause or roll back a rollout when the failure rate passes your threshold
  • Observe compares the new version with the previous one before you raise exposure
Progressive rollouts docs

1–5%

A typical first rollout step

Automatic rollback

Every update has to prove it starts. If a new bundle does not call notifyAppReady() in time, the device goes back to the last working bundle and marks the new one as failed.

  • Rollback triggers if notifyAppReady() isn't called within appReadyTimeout (10 seconds by default)
  • Roll a whole channel back to any earlier bundle from its history
notifyAppReady() docs

10s

Default appReadyTimeout before automatic rollback

Store-review aware delivery

Capgo delivers the Capacitor web layer: JavaScript, CSS, and assets. It does not change the native binary, plugins, permissions, entitlements, or app-store metadata. Store review is app-specific, so you remain responsible for policy compliance and approval.

  • Use a native store release when native capabilities, plugins, permissions, or app-store metadata change
  • Keep reviewer notes clear about the app’s intended functionality and web-layer update path
  • Review the current Apple and Google policies before each submission
  • Read Capgo's store-policy guidance
  • Apple guidelines
  • Google Play policy

FAQ

Questions production teams ask

How updates reach devices, and what to do when one goes wrong.

When do users get a live update?

By default, the app checks for updates when it comes to the foreground and every 10 minutes while it stays open. It downloads the new bundle in the background, installs it when the user leaves the app, and runs it the next time they open it. The autoUpdate setting changes this behavior.

Update behavior docs

Can devices pick up an urgent fix faster?

Yes. After you change a channel's bundle, send an update notification from the console, or add --send-update-notification to bundle upload. Devices get a silent push and check right away. This needs Capgo Notifications with iOS and Android push credentials. Delivery is best effort: an offline or force-quit app checks on its next launch.

Send update notification

What happens if an update breaks the app?

If a new bundle does not call notifyAppReady() within 10 seconds (the default appReadyTimeout), the device returns to the last working bundle and marks the new one as failed. For bugs that do not stop the app from starting, roll back the progressive rollout or pick an earlier bundle from the channel history.

Rollbacks docs

How do we release to a few users first?

Upload with --rollout to send the bundle to a random, sticky share of the channel while everyone else stays on stable. Raise the percentage, promote, or roll back from the CLI or console. Auto-pause can stop exposure when the failure rate passes a threshold.

Progressive rollouts docs

What can't a live update change?

Live updates replace the web layer: JavaScript, HTML, CSS, and assets. Native plugins, Capacitor upgrades, capacitor.config changes, and iOS or Android project files need a store release. Capgo checks bundles for native compatibility on upload, and channels can block updates to older binaries.

Native compatibility docs
