Where startup time goes

Release work competes with product work

Store review sits on small fixes

A one-line JavaScript fix waits for a new binary and store review, often 24–48 hours, sometimes much longer. Then users still have to update.

Nobody owns the build machine

iOS builds need a Mac, signing certificates, and provisioning profiles. On a small team, that work lands on whoever is free that day.

A bad release is hard to undo

Without a rollback path, a broken screen stays live until the next binary is approved and installed.

How it works

How a startup team ships with Capgo

From the first upload to a CI pipeline. Every command below is from the Capgo CLI docs.

  1. 1

    Add Capgo to your app

    The init command walks you through adding the updater plugin, building, and uploading your first bundle.

    npx @capgo/cli@latest init
    Quickstart
  2. 2

    Upload from CI

    Save your Capgo API key as CAPGO_TOKEN in your CI secrets and add one upload step after the web build.

    # After your web build, with CAPGO_TOKEN set in CI secrets
npx @capgo/cli@latest bundle upload --channel production
    GitHub Actions guide
  3. 3

    Roll out to a share of users

    Send the new bundle to 10% of production devices. Promote it to everyone when install and failure data look right.

    npx @capgo/cli@latest bundle upload --channel production --rollout 10
npx @capgo/cli@latest channel set production --rollout-promote
    Progressive rollout docs
  4. 4

    Build native binaries in the cloud

    Save your signing credentials once, then request iOS and Android builds from your laptop or from CI.

    npx @capgo/cli@latest build credentials save --appId com.example.app --platform ios
npx @capgo/cli@latest build request com.example.app --platform ios
    Capgo Build docs

Startup questions

What small teams ask before adding Capgo to their release process.

How much does Capgo cost?

See pricing

Do we need a DevOps engineer to set this up?

No. Setup is the init command plus one upload step in your CI. Capgo runs the update servers, the bundle storage, and the build machines.

CI integration docs

What can we ship without a store review?

Changes to JavaScript, HTML, CSS, and assets. Native code, new plugins, and permission changes need a new binary. Capgo checks bundle compatibility with the native side before upload.

Native compatibility docs

What happens if we ship a broken update?

If the new bundle does not call notifyAppReady() within 10 seconds, the device goes back to the previous working version. You can also point a channel back to an earlier bundle.

Rollback docs

Do we need a Mac for iOS builds?

No. Capgo Build runs iOS builds on Capgo's Mac machines and can upload the result to App Store Connect.

iOS build docs
