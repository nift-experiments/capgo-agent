Why retail teams add a live update lane

Campaign dates don't move for store review

A campaign-day bug on the store-only path

A sale starts and the promo code field fails on one platform. The fix is a few lines of JavaScript.

With a store-only process, you build a new binary and submit it. Store review is often 24–48 hours, sometimes much longer.

Even after approval, shoppers still have to install the new version. The campaign may be over before most of them do.

Campaigns run on fixed dates

Promotions, product drops, and seasonal sales start at a set time. A web-layer fix should not depend on a review queue.

Checkout changes need care

A change to the cart or checkout should reach a small share of shoppers first, with a fast way back.

Many app versions stay installed

Shoppers update at different times. A bundle that needs new native code must not reach older binaries.

Campaign screens need a real-device check

Marketing and QA want to see the campaign screens on a phone before they go live.

How it works

How retail teams ship a campaign change with Capgo

A typical flow for a promo or checkout change in a Capacitor shopping app. Every command below is from the Capgo CLI docs.

  1. 1

    Stage it on a staging channel

    Upload the campaign bundle to staging and scan the QR code to open it on a real device. Bundle preview must be enabled for the app.

    npx @capgo/cli@latest bundle upload --channel staging --qr-preview
    Channels docs
  2. 2

    Send it to a share of shoppers

    Upload to production with --rollout. Most shoppers stay on the stable bundle until you promote.

    npx @capgo/cli@latest bundle upload --channel production --delta --rollout 10
    Progressive rollouts docs
  3. 3

    Promote when checkout looks right

    Check install and failure data in Capgo and your own sales dashboards, then promote the bundle to every device on the channel.

    npx @capgo/cli@latest channel set production --rollout-promote
    Observe docs
  4. 4

    Roll back if it doesn't

    Send the rollout cohort back to stable in one command, or pick an earlier bundle from the channel history.

    npx @capgo/cli@latest channel set production --rollout-rollback
    Rollbacks docs

FAQ

Questions retail teams ask

What a live update can change in a shopping app, and how to keep checkout safe.

Can we change prices or checkout with a live update?

Prices usually come from your backend, so change them there. A live update changes the web code and assets that display them: promo banners, product pages, cart and checkout screens. Changes to native payment SDKs or plugins need a store release.

Native compatibility docs

Is Capgo an A/B testing tool?

No. A progressive rollout sends a bundle to a random, sticky share of devices to limit risk. It does not measure conversion. For experiments, use your analytics or feature flag tool. Use channels when specific users need a different bundle.

Progressive rollouts docs

How do we test campaign screens before they go live?

Upload the bundle to a staging channel and open it on a device with a QR code, or pin test devices to that channel with a device override. Promote the same bundle to production when it is approved.

Channels docs

What if a release breaks checkout?

If the new bundle fails to start and never calls notifyAppReady(), the device rolls back by itself. If it starts but checkout misbehaves, roll back the progressive rollout or pick the previous bundle from the channel history.

Rollbacks docs

When do shoppers see the update?

By default, devices download it in the background and run it the next time the app comes back to the foreground. If shoppers must see it on the first screen, use a direct update mode such as onLaunch.

Update behavior docs
