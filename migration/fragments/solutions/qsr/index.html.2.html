Why restaurant teams add a live update lane

Menus and promotions change faster than store releases

A launch-day bug on the store-only path

A limited-time item goes live on a set date. On launch morning, QA finds that it does not show in the app menu.

The fix is in the web layer, but a store-only process means a new binary and store review, which is often 24–48 hours, sometimes much longer.

Even after approval, customers still have to install the update, and in-store kiosks need their own update path.

Promotions have fixed dates

A limited-time offer starts when the campaign starts. A web-layer fix should not wait for a store release.

Several brands and markets

Each brand app and each market can need different menus, promotions, and legal text from the same codebase.

Changes need a pilot first

A new ordering flow should run in one market or a few test devices before it goes everywhere.

Peak hours leave no room for errors

A broken ordering screen at lunch needs a way back that does not depend on a store release.

Ship on your schedule, per market and brand

Upload from CI at the time you pick

Capgo has no release scheduler. Your CI triggers the upload: on merge, on a manual run, or on a cron schedule you set for the launch.

  • Guides for GitHub Actions, GitLab CI, Bitbucket, and Azure DevOps
  • Keep the Capgo API key in your CI secrets
  • Roll back from the console or CLI if the launch goes wrong
GitHub Actions guide CI/CD integrations 
# .github/workflows/capgo-launch.yml
on:
  workflow_dispatch:
  schedule:
    - cron: '0 6 15 11 *' # 06:00 UTC on 15 Nov, your launch time

jobs:
  upload:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - run: npm ci && npm run build
      - run: npx @capgo/cli@latest bundle upload --channel production --delta
        env:
          CAPGO_TOKEN: ${{ secrets.CAPGO_TOKEN }}
# one app ID per brand, same web codebase
npx @capgo/cli@latest bundle upload com.yourgroup.brand-a --channel production
npx @capgo/cli@latest bundle upload com.yourgroup.brand-b --channel production

Channels for markets and pilot groups

Create a channel for each market, region, or pilot group. The app joins with setChannel() on channels that allow self-assignment, and your team can pin a device with an override.

  • Channels for markets, regions, or pilot stores
  • Devices join with setChannel() or device overrides
  • Progressive rollout inside each channel
Channels docs Progressive rollouts docs 
// in the app, after the user or kiosk picks a market
import { CapacitorUpdater } from '@capgo/capacitor-updater'

await CapacitorUpdater.setChannel({ channel: 'market-uk' })

CapacitorUpdater: { autoUpdate: 'onlyDownload' }

CapacitorUpdater.addListener('updateAvailable', ({ bundle }) => {
  next = bundle

// when the kiosk is back on its idle screen

Kiosks that stay open all day

The default mode applies updates when the app goes to the background, which a kiosk rarely does. Download updates automatically and apply them when the kiosk is idle.

How it works

How restaurant teams ship a menu change with Capgo

A typical flow for a promotion that starts in one market. Every command below is from the Capgo CLI docs.

  1. 1

    Create a channel per market or pilot

    Allow self-assignment so the app can join the channel for the market the user or kiosk is in.

    npx @capgo/cli@latest channel add market-uk --self-assign
    Channels docs
  2. 2

    Upload the promo to part of the market

    Run this from CI at launch time. The rollout sends the bundle to a share of devices on the channel while the rest stay on stable.

    npx @capgo/cli@latest bundle upload --channel market-uk --delta --rollout 10
    Progressive rollouts docs
  3. 3

    Promote when orders go through

    When ordering works as expected, promote the bundle to every device on the channel.

    npx @capgo/cli@latest channel set market-uk --rollout-promote
    Progressive rollouts docs
  4. 4

    Roll back during a rush

    If ordering breaks, send the rollout back to stable, or pick the previous bundle from the channel history in the console.

    npx @capgo/cli@latest channel set market-uk --rollout-rollback
    Rollbacks docs

FAQ

Questions restaurant teams ask

Timing, kiosks, markets, and what a live update can change.

Can we schedule a menu launch?

Capgo does not have a release scheduler. Trigger the upload from your CI at the time you choose, for example with a scheduled GitHub Actions workflow or a manual run on launch morning. If the new UI must stay hidden until a date, gate it in your app or backend.

GitHub Actions guide

How do kiosks get updates if the app never closes?

In the default mode, updates apply when the app goes to the background, which a kiosk rarely does. Set autoUpdate to 'always' to apply updates during the periodic check (every 10 minutes by default), or to 'onlyDownload' and call set() when the kiosk returns to its idle screen.

Update behavior docs

Can each market or brand run a different version?

Yes. Give each brand its own app ID in Capgo, and give each market or pilot group its own channel. Devices join a channel with setChannel() when self-assignment is allowed, or through a device override.

Channels docs

What if a promo release breaks ordering?

Roll back the progressive rollout or pick the previous bundle from the channel history. If the new bundle fails to start and never calls notifyAppReady(), the device returns to the last working bundle by itself.

Rollbacks docs

Can a live update change menu prices?

Prices usually come from your backend or POS integration, so change them there. A live update changes the web screens that display the menu and prices. Native plugins, payment SDKs, and Capacitor upgrades need a store release.

Native compatibility docs
