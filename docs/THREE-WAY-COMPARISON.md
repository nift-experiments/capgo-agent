# Capgo three-way experiment — final comparison

The pinned English production frontend can be reproduced with Nift while preserving its appearance, routes and content. Faithful Capgo preserves the authoring corpus and regenerates MDX/Markdown bodies and metadata; Agent maintains converted HTML with shared Nift structure and independently compiled readable browser controllers. These are bounded frontend migrations, not recreations of Capgo’s private services.

## Fixed inputs and measured results

Upstream is official `Cap-go/website` at `7d5b69d6ba8a6630384dffc7d012431ee3ed22ec`. Faithful is closed at `590c1eec`; no further faithful refactoring was performed for this phase. Agent browser/native architecture is `fbc7bb5`, with the permitted incremental-dependency correctness correction at `6371356`, the exact repeated benchmark revision. Final evidence/docs commits do not change this architecture. AGPL source attribution and bundled dependency licences remain.

Measured full-build elapsed ratios are approximately 18.7× upstream/faithful, 47.6× upstream/Agent and 2.5× faithful/Agent. These describe the recorded workflows, not equivalent-work compiler speed. Astro rebuilds frontend bundles and renders authored content. Faithful reuses compiled frontend assets and, warm, prepared MDX/content. Agent keeps already-converted HTML, retains production CSS/images/fonts, and independently bundles native JS on each normal Nift invocation. Thus Agent’s content work is smaller than faithful’s. Its incremental edits are HTML edits; faithful’s edit families are authored MDX/Markdown/marketing inputs, not identical edits.

All Nift timings use ordinary full or incremental CLI builds, threads `-1`, installed Nift 4.6.0 on Intel i7-12700H / 20 logical CPUs. GNU time RSS means maximum process memory, not simultaneous process-total memory. Dependency install and edit restoration are excluded. Node 22.22.1 for Nift, Bun 1.4.2 / Node 24.21.0 for upstream. Same recorded Nift binary hash; source commit is unavailable and explicitly not invented. Warm system page cache is not flushed. Raw Agent methodology, commands, source/output edit verification and measurements: `../evidence/final-benchmarks/`; faithful/upstream evidence remains in the frozen faithful repo. The historical 1.98s single Agent sample is superseded. Faithful’s earlier 4.40s versus final 5.67s difference remains in its report; this comparison does not erase it.

## Fidelity and runtime

All three share the 1,347 captured HTML routes. Agent verifies every retained file plus all rebuilt native assets and exact HTML bytes. Faithful reports exact parsed heads and semantic body equivalence, with 1,192 accepted body-byte differences. Both report zero introduced semantic/link issues; the oracle’s 11,339 existing link/anchor issues are preserved. Missing translated destinations remain upstream quirks, not invented local routes.

Agent’s representative browser matrix covers 13 page classes at desktop/mobile, production output as oracle, plus navigation, search, tabs, copy, TOC, forms, pricing, language choices and keyboard/focus checks. Eighteen of 26 paired viewport screenshots have no thresholded pixel difference; other differences are under 1%, including animation timing. This is representative evidence, not exhaustive full-page or accessibility certification. Search returned actual Algolia results; data-unavailable states match the reference. External service content and availability can change.

Account creation, authenticated workflows, device identifiers, genuine signing success and browser certificate upload/download remain uncertified. No accounts or external messages were created. Agent’s allowlisted provider adapter has local mock tests for method/schema/errors and token forwarding, and can connect compatible own services; it does not implement those services. See `INTERACTION-MATRIX.md`, `CLEAN-CHECKOUT.md` and `NATIVE-ARCHITECTURE.md` for exact evidence and own-provider configuration. Faithful’s original signing/device server routes remain unsupported locally and its earlier adapter does not automatically reconnect retained controllers. Static parity is never proof of backend success.

## What machinery changed

Agent maintains 1,347 Nift wrappers, 1,881 shared HTML includes, 5,990 converted HTML fragments and six templates/helpers. Wrapper bytes are 11,474,495 after explicit dependency declarations; include and fragment bytes are 24,595,477 and 70,519,275. Converted markup is substantial maintained source, not a compact hand-written content model. Thirty-seven readable JS files (290,686 bytes) supply all 21 recovered entry controllers. No Astro build/runtime or React install is required; zero Astro hydration islands occur. Existing scope IDs remain for CSS parity.

DocSearch is the documented reactive exception: Preact compatibility supports its existing keyboard, focus, ranking, history and modal state. Wrapper initial JS is 1,644 bytes, complete reachable search graph 134,776 uncompressed bytes. Mermaid remains a specialised rendering dependency: initial graph 716,083 bytes, all reachable lazy modules 5,189,923 bytes, not all downloaded on every page. SDK/Supabase/crypto helpers remain explained dependencies. Inline production controllers/configuration and external analytics/testimonials are classified retained implementation, not claimed newly designed vanilla replacements.

The 103 unreferenced old JS assets (5,457,094 bytes) were removed from served output only after reference auditing; their oracle copies remain for evidence. All rebuilt Agent JS totals 6,082,284 bytes versus original 6,073,203 bytes: essentially the same, slightly larger. There is **no demonstrated overall client-JS reduction**. Upstream already compiled much of the site to ordinary HTML/JS. The gain is source/runtime accountability and removal of Astro from normal authoring/build prerequisites, not a fictitious removal of megabytes of hydration. All versions retain the original CSS/images/fonts; Agent retains 19 CSS files / 627,800 bytes.

Agent lockfile has 187 packages; installed regular dependency files total 228,622,975 bytes / 11,529 files (not allocated disk size or a network-download metric). Faithful root lock has 188 packages, but also uses the separate locked MDX renderer and other renderer inputs, so these root counts are not whole-system comparable footprints. Upstream’s monorepo/Bun workspace scope differs. Equivalent total install/download footprints were not measured; no percentage reduction is claimed. Full current accounting is `../evidence/runtime/architecture-audit.json`.

## Maintenance investigation: evidence before preference

This reporting checkpoint replaces the earlier recommendation to retain Astro because of its “content/component/i18n model and established integrations.” That phrasing was too broad. The comparison below inspects the pinned source and both finished implementations; it does not modify any implementation or remeasure builds. Operation comparisons are source-traced, not timed usability studies. Team familiarity, future maintenance throughput and ecosystem size were not measured.

### 1. Actual content models and editing operations

Upstream docs live in `apps/docs/src/content/docs`, loaded with Starlight `docsLoader()` and `docsSchema()`. Blog entries live in `apps/web/src/content/blog`; tutorials in `apps/web/src/content/plugins-tutorials`. Web `content.config.ts` uses glob loaders and Zod: blog `title`, `slug`, author fields, dates, tag and a supported `locale` are declared; dates are transformed, `origin` defaults to `ai`, and tags are normalised. Plugin platform status is restricted to `supported`, `partial`, `unsupported`. Blog routes query `getCollection('blog')`, filter publication/origin and call `render(entry)`. Product/marketing/legal pages are `.astro` pages composing components and config; listing pages query collections. These are actual configured behaviours, not a generic assertion that Astro has content collections. Sources: [web schema](https://github.com/Cap-go/website/blob/7d5b69d6ba8a6630384dffc7d012431ee3ed22ec/apps/web/src/content.config.ts), [docs schema](https://github.com/Cap-go/website/blob/7d5b69d6ba8a6630384dffc7d012431ee3ed22ec/apps/docs/src/content.config.ts), [blog route](https://github.com/Cap-go/website/blob/7d5b69d6ba8a6630384dffc7d012431ee3ed22ec/apps/web/src/pages/blog/%5Bslug%5D.astro).

Faithful keeps authored inputs under `corpus/authored`, reconnecting docs MDX/Markdown and web content through `migration/web-sources.json`, docs mappings, prepared metadata and Nift wrappers. `tools/prepare-web.mjs` hashes authored inputs and adapter dependencies; `tools/render-blog-listing.mjs` discovers English blog files, parses YAML and filters published entries. `tools/authored-content.mjs` provides a deliberately narrow plugin collection API, not the complete upstream `astro:content` API. Metadata preparation uses YAML and recovered head logic. Nift `@input`, functions, explicit dependencies, scripting and the locked MDX renderer provide content composition and incremental rendering. Evidence: [faithful preparation](https://github.com/nift-experiments/capgo/blob/590c1eec/tools/prepare-web.mjs), [listing adapter](https://github.com/nift-experiments/capgo/blob/590c1eec/tools/render-blog-listing.mjs), [collection adapter](https://github.com/nift-experiments/capgo/blob/590c1eec/tools/authored-content.mjs), [docs metadata](https://github.com/nift-experiments/capgo/blob/590c1eec/tools/render-docs-metadata.mjs).

Agent’s authoritative rendered source is `migration/pages`, converted `migration/fragments`, shared `migration/includes` and templates. Historical MDX/prototype files are not the normal authoring pipeline. Route wrappers explicitly declare raw fragment and shell dependencies; readable browser sources compile independently. HTML is not converted back into MDX. Existing page text is changed directly in its mapped fragment; output propagation is verified in the real-edit benchmarks. That is a different authoring workflow, not proof that HTML is intrinsically harder to maintain when agents perform edits.

| Concrete operation | Upstream Astro | Faithful Nift | Agent Nift | Classification / conclusion |
|---|---|---|---|---|
| Edit an existing docs paragraph | Edit MDX; configured loader/render handles it | Edit corresponding authored MDX; hook prepares changed content and Nift renders it | Edit mapped HTML fragment; ordinary dependency tracking rebuilds it | Different workflow. Full-corpus support exists in all; no demonstrated universal Astro advantage |
| Reject invalid blog locale or plugin platform status | Explicit collection Zod schema rejects an out-of-set value during collection processing | Current YAML adapters do not apply the complete upstream collection schema; output/renderer checks are narrower | No equivalent authoring frontmatter contract in the HTML workflow | Experiment/tooling gap. A schema preprocessor is composable; not intrinsic inability of Nift to validate content |
| Add a new published blog route | Glob discovery + `getStaticPaths` enumerate published entries | Listing loader can see a new file, but rendered body/metadata mappings and Nift route registration must also be extended | Add wrapper/body/head, listing/nav references and route registration | Current migration convenience gap: automatic discovery versus explicit source mappings. Not an inherent Nift route-generation limit |
| Change collection taxonomy across listings | Schema tag normalisation + collection queries are central entry points | Adapter/data dependencies must be updated consistently; current card adapter splits tags directly | Edit relevant shared/listing fragments or apply validated bulk transformations | Concrete adapter/workflow difference; parity of the captured corpus does not certify arbitrary new taxonomy changes |
| Change product copy/layout | Edit the `.astro` page or shared component/config | Edit registered authored template/data, within adapter support | Edit shared include or relevant HTML fragment | Existing operations supported. Arbitrary new Astro syntax is not guaranteed by bounded adapters; no timed productivity ranking |

A new route/content change intentionally departs from a frozen golden reference: maintainers must update the oracle or accept/document the departure. This is the experiment’s validation policy, not a framework limitation. All three can model content; the defensible upstream convenience is integrated schema/discovery/query tooling. We have not demonstrated a fundamentally superior content capability or general editing UX.

### 2. Components, composition and browser state

Upstream `CommandCode.astro` has a declared `Props` interface, token transformation and repeated span generation. `comparison/ComparisonPage.astro` composes named slots (`after-table`, `after-migration`). Several components contain scoped `<style>` blocks; the compiler produces style scope IDs. These offer concrete source conventions and automatic style scoping. A `Props` interface is a compile-time/type-tooling affordance, not proof of runtime validation or that `astro check` passed; some docs overrides explicitly use `@ts-nocheck`. Sources: [CommandCode](https://github.com/Cap-go/website/blob/7d5b69d6ba8a6630384dffc7d012431ee3ed22ec/apps/web/src/components/CommandCode.astro), [comparison slots](https://github.com/Cap-go/website/blob/7d5b69d6ba8a6630384dffc7d012431ee3ed22ec/apps/web/src/components/comparison/ComparisonPage.astro), [scoped header styles](https://github.com/Cap-go/website/blob/7d5b69d6ba8a6630384dffc7d012431ee3ed22ec/apps/web/src/components/Header.astro).

Faithful’s bounded `tools/authored-template.mjs` evaluates registered presentational components, children and `childSlots`; shared shells and Nift functions/includes recover composition. Thus named composition and parameterisation were not absent. Agent uses ordinary includes/functions and route-specific substitutions; repeated markup/controller inputs are explicit. For this captured site that composition produces exact HTML. Its zero Astro hydration islands and 21 readable entry controllers demonstrate that maintaining upstream component abstractions is not required for these delivered interactions.

The genuine limitation is **this migration’s** bounded Astro-source adapter and retained compiled CSS: introducing an unsupported syntax pattern or changing scoped styles may require adapter work and independently regenerating/scoping CSS. Upstream supplies that compiler pipeline automatically. Agent chooses direct HTML/CSS composition rather than Astro props/slots; this is a workflow difference, not a missing ability to pass parameters or generate repeated structures. No equivalent new-component/style-change maintenance benchmark was run. Sources: [faithful component adapter](https://github.com/nift-experiments/capgo/blob/590c1eec/tools/authored-template.mjs), [Agent shell function](https://github.com/nift-experiments/capgo-agent/blob/6371356/migration/templates/docs-shell.f).

Browser state is a separate dimension: navigation, tabs, forms and map controllers are ordinary JS in Agent; DocSearch justifies a Preact compatibility library for focus/modal/search state; Mermaid remains specialised. Framework islands can be composed where useful. No discovered Capgo interaction requires Astro itself. The similar total client-JS sizes prevent a claim that removing the build framework removed all browser complexity.

### 3. Capgo localisation is an edge system, not an Astro category win

The common Astro config sets `i18n.locales` to **only `[defaultLocale]`**, English. Web/docs locale services advertise nine choices, but describe them as edge-worker paths. Shared `copy/messages.ts` is static English copy; its comment directs new strings through `bun run generate:message-contexts` for the separate translation system. The docs override computes language links itself. The docs llms integration explicitly says translated paths are served at request time by the edge translation worker. Sources: [shared Astro config](https://github.com/Cap-go/website/blob/7d5b69d6ba8a6630384dffc7d012431ee3ed22ec/apps/shared/astro-config.mjs), [locale service](https://github.com/Cap-go/website/blob/7d5b69d6ba8a6630384dffc7d012431ee3ed22ec/apps/web/src/services/locale.ts), [English messages](https://github.com/Cap-go/website/blob/7d5b69d6ba8a6630384dffc7d012431ee3ed22ec/apps/shared/copy/messages.ts), [language menu](https://github.com/Cap-go/website/blob/7d5b69d6ba8a6630384dffc7d012431ee3ed22ec/apps/docs/src/components/doc/LanguageSelect.astro).

`apps/translation-worker/src/index.ts` recognises eight non-English prefixes, fetches the English origin, rewrites local URLs/redirects and HTML language/alternate hreflang links, and stores translated page/state records. Its configuration supplies a translation store, coordinator, AI model and queues. Pending translation can produce an English retry response with HTTP 503/Retry-After, or a temporary English redirect; origin 404/410 is handled distinctly. This is not simply “Astro falls back to English.” [Worker implementation](https://github.com/Cap-go/website/blob/7d5b69d6ba8a6630384dffc7d012431ee3ed22ec/apps/translation-worker/src/index.ts), [deployment configuration](https://github.com/Cap-go/website/blob/7d5b69d6ba8a6630384dffc7d012431ee3ed22ec/apps/translation-worker/wrangler.jsonc).

| Operation / boundary | What the source actually requires | Nift comparison |
|---|---|---|
| English content + language metadata | English source, head logic and advertised locale URLs | Faithful regenerates heads; Agent preserves exact HTML, including language/alternate links |
| Translated content storage/generation | Worker store/cache/queues and request-time translation, not a captured nine-locale static docs tree | Neither Nift implementation deploys/certifies this worker. Captured English build likewise is not evidence of production translation success |
| Shared translated strings | English keys + generated contexts/manual context overrides feed worker translation | Faithful preserves authored copy inputs; Agent has converted text. Agent key-level copy updates require mapped/bulk edits and context management if reusing the worker |
| Add a locale | Update web/docs locale arrays, names/types, worker supported-locale set and relevant translation configuration/context; validate menus/heads and deployed translation | No tested file-count or effort comparison. Nift menus/head generation/source mappings also need updates; worker integration remains outstanding |
| Add a translated page | English origin page plus worker translation/storage lifecycle | No intrinsic Astro requirement was identified at the HTML-origin boundary; compatibility with Nift output is plausible but has not been tested |
| Missing translation validation/fallback | Worker state/retry logic, not just static collection schemas | Missing locale routes in local previews are preserved capture limitations; they are not a successful multilingual implementation |

The upstream project has the translation system already implemented, which is a real **implementation coverage/incumbency** advantage. Its deployment/storage/context requirements remain even if Astro is replaced. We withdraw the claim that Astro’s i18n model was demonstrated superior for Capgo. Serving equivalent English HTML does not by itself certify worker interoperability; neither do the static language menus prove locale completeness.

### 5. Nift as programmable orchestration

This experiment provides direct evidence, not just a feature list. Faithful’s Nift `run("node", "tools/pre-build.mjs")` hook invokes ordered/concurrent content, code and metadata preparation. Node transforms authored data and hashes dependencies; Nift consumes generated files through templates and explicit dependencies. Agent’s hook invokes independent esbuild; its normal runtime connects fixed HTTP contracts to a configurable provider. Browser packages are bundled with readable inputs. These demonstrate content preprocessing, external processes/package functionality, JSON transformation, generated assets, prepared MDX and arbitrary preparation at build seams. [Faithful hook](https://github.com/nift-experiments/capgo/blob/590c1eec/tools/pre-build.f), [orchestrator](https://github.com/nift-experiments/capgo/blob/590c1eec/tools/pre-build.mjs), [Agent hook](https://github.com/nift-experiments/capgo-agent/blob/6371356/tools/pre-build.f), [JS preparation](https://github.com/nift-experiments/capgo-agent/blob/6371356/tools/native-controllers.mjs).

Live API acquisition could use the same fetch/transform seams; here much build data deliberately uses recorded responses. Independent CSS/route/translation generators can be connected at those seams, but are not fully rebuilt in these frozen projects. Native/FFI functionality was not exercised by this Capgo checkpoint; it is neither needed for the demonstrated integrations nor counted as evidence of a completed port. Nift is the build/composition layer, not a substitute for an HTTP server or cloud service.

### 6. Convenience, ecosystem and capability are separate

The pinned upstream project actually uses packaged MDX, Starlight, DocSearch, sitemap, icon and Tailwind/Vite integrations. That demonstrates **available turnkey adapters for this stack**, while the migrations own several explicit adapters and preparation scripts. It does not measure community size, documentation quality, hiring pool or maintenance productivity. Broader ecosystem maturity may affect an organisation’s choice, but was not quantified here. Team familiarity is unknown; incumbency means migration/acceptance work can be avoided, not that Astro is inherently better.

All identified Nift drawbacks above are either **experiment coverage gaps** (translation/private services, retained generation artifacts), **migration tooling gaps** (complete collection schema/discovery, broader source adapter/scoped-style pipeline), or **different workflows** (converted HTML/agent edits). No intrinsic architecture prohibition was demonstrated. A particular missing convenience should be specified and potentially improved, not promoted into an interoperability deficit. Neither framework-specific adapter counts nor benchmark ratios establish universal maintainability.

### 7. What would we maintain, from this evidence?

For an organisation explicitly adopting Nift while preserving Capgo’s authoring corpus, **faithful Nift is a credible preference**: full captured corpus support, high fidelity and measured faster/lighter build workflows are demonstrated. Before treating it as the evolving production source, we would require explicit acceptance of new-route/schema/style-generation workflows and deployment/integration certification. That work concerns the present migration, not an inability of Nift to model the site.

For an organisation choosing **agent-mediated routine implementation**, **Agent is the implementation that matches that premise**: direct inspectable markup, maintained controllers, deterministic mappings, strong parity gates and a 1.04–1.09s measured HTML edit loop. Humans retain intent, architecture and acceptance. Agent’s many fragments are a representation choice; the experiment did not measure whether agents maintain them more reliably or cheaply than MDX. It should not be penalised merely because manual bulk editing is tedious, nor awarded an unmeasured productivity victory.

For the existing production organisation with no migration requirement, **keeping upstream avoids migration and new certification work**, and retains its already-implemented translation/deployment system and configured collection/compiler conveniences. That is a conditional transition-cost/coverage argument. We did not measure the team’s familiarity, establish superior fundamental content/composition/i18n capability, or find external systems Nift cannot integrate with.

If we owned Capgo and were selecting a future workflow, the evidence supports choosing faithful for preserved MDX + Nift, or Agent for directed agent editing; it does **not** justify an unconditional “retain Astro” recommendation. A final production choice needs the organisation’s priorities and certification of changing-content/deployed-service workflows. The comparison need not assign every implementation a win: Nift wins the measured local build/resource workflows; upstream presently supplies specified turnkey conveniences and implementation coverage; general maintenance productivity remains unmeasured. Both Nift architectures remain frozen; this is a reporting correction only.
